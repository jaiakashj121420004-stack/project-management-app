# SETUP-MCP.md — Connect Claude to your Aurora account

> How a user connects Claude Desktop or Claude Code to their own Aurora account
> (read/write boards, to-dos, notes) — the same shape of integration Obsidian
> offers via its community MCP server. For the deploy/ops checklist see
> [supabase/README.md](./supabase/README.md) → "Aurora MCP server". For
> everyday rules see [CLAUDE.md](./CLAUDE.md); for the full spec see
> [plan.md](./plan.md).

## For you (connecting Claude)

1. In Aurora, go to **Settings → Connect Claude** (Pro and above). Click
   **Generate access token**. Copy it immediately — Aurora shows it exactly
   once and never stores the plaintext, so if you lose it you'll need to
   regenerate (which invalidates the old one).
2. Pick your client:
   - **Claude Code:** copy the `claude mcp add ...` command shown under the
     token and run it in a terminal.
   - **Claude Desktop:** copy the JSON shown and paste it into your
     `claude_desktop_config.json`'s `mcpServers` object (create the file if it
     doesn't exist — Claude Desktop → Settings → Developer → Edit Config).
     Fully restart Claude Desktop afterward.
3. Ask Claude to list your projects, add a card, or check today's to-dos to
   confirm it's connected.
4. To disconnect at any time, click **Disconnect** in Settings — the token
   stops working immediately, everywhere it's configured.

**Available tools:** `list_projects`, `list_board_cards`, `create_card`,
`update_card`, `list_todos`, `add_todo_item`, `toggle_todo_item`,
`list_notes`, `read_note`, `append_to_note`. Deliberately not included in v1
(SIMPLICITY-GUARDRAIL discipline — see the decision log in `memory.md`): canvas
tools, member/sharing tools, delete tools, bulk operations. Everything a tool
does is still governed by your normal Aurora permissions — Claude can't see or
touch anything you couldn't yourself.

## Why this was built this way (technical record)

This is genuinely new architecture for this codebase — the first server
process outside the existing Edge Function CRUD pattern, and the first Edge
Function that acts on behalf of a specific user under real Row Level Security
rather than the service role. Decisions, and what was rejected:

**Hosting — a Supabase Edge Function, not a new Cloudflare Worker.** Supabase
documents and demonstrates hosting an MCP server this way (their own
[BYO-MCP guide](https://supabase.com/docs/guides/getting-started/byo-mcp) and
a worked [mcp-lite example](https://supabase.com/docs/guides/functions/examples/mcp-server-mcp-lite)),
and it keeps this repo's "one deploy mechanism" rule intact. The library used
is [mcp-lite](https://github.com/fiberplane/mcp-lite) — a small, near-zero-
dependency, fetch-first MCP framework — over the heavier official
`@modelcontextprotocol/sdk`, whose confirmed transport surface is Node-
`http`-oriented; mcp-lite is what Supabase itself demonstrates working
end-to-end on Edge Functions.

**Auth — a personal access token, not OAuth, for v1.** As of mid-2026, Claude
Desktop's "Custom Connectors" GUI only supports OAuth client id/secret in
Advanced Settings — there is no raw bearer-token field (tracked in several open
`anthropics/claude-ai-mcp` issues). Building a full OAuth 2.1 authorization
server (dynamic client registration, consent UI, refresh tokens) is a separate
project not justified for v1. Instead: a scoped, revocable, hashed personal
access token (`profiles.mcp_token_hash` — **only the SHA-256 hash is ever
stored**; the plaintext is generated by `mcp-token` and shown once), connected
via Claude Code's native `--header` support or, for Claude Desktop, the
[`mcp-remote`](https://github.com/geelen/mcp-remote) local bridge (also reads a
custom `Authorization` header). This is also why `mcp-server` is deployed
`--no-verify-jwt` — Supabase's platform JWT gate expects a Supabase session
JWT, not Aurora's own PAT, in the `Authorization` header.

**Authorization inside `mcp-server` — real RLS, not a service-role shortcut.**
This is the one place this integration could quietly have taken a shortcut,
and deliberately doesn't. On a valid token, the function mints a short-lived
(5 min) Supabase-compatible access token for that user (`sub: user_id, role:
authenticated`), signed with a **dedicated** JWT signing secret
(`MCP_JWT_SIGNING_SECRET`, added via Dashboard → Auth → JWT Signing Keys —
separate from the project's default session key, so revoking it if this
integration is ever compromised never touches real user logins). Every tool
handler then talks to PostgREST using *that* minted token, never the service
role — the same RLS policies (`is_project_member`, `can_edit_card`, …) that
govern the app itself decide what a tool can see or change. Plain Web Crypto
(`crypto.subtle`) signs the token — no `jose` dependency, matching this repo's
existing Edge Functions, which have zero runtime npm dependencies.

**Rejected: `auth.admin.generateLink` + `verifyOtp`** (Supabase's other
documented "become this user" pattern). It rides Supabase Auth's
email-sending rate limits even when no email is actually sent — on the free
tier this project runs on, that's a handful of requests per hour, which would
make an agentic client calling several tools in one turn fail intermittently.
A self-signed JWT with a dedicated key has no such limit.

**Token model — one active token, hashed, shown once.** Deliberately not a
GitHub-style multi-named-token list (SIMPLICITY-GUARDRAIL: no new maintenance
surface — a list/create/delete UI — without a demonstrated need). Regenerating
invalidates the previous token everywhere it's configured.
